# Поиск: сервис и ajax

## PHP

```php
if(\Bitrix\Main\Loader::includeModule('shef.toolsaikb'))
{
	$articles = \Shef\ToolsAiKb\Public\Service\KbSearchService::find('Как настроить квоту?', 5);
}
```

`find(string $query, int $limit = 5): array` — список
`['id' => int, 'title' => string, 'url' => string, 'noteUrl' => string, 'snippet' => string, 'text' => string]`:

- `id` — документ `note`;
- `url` — от корня портала: адрес статьи в родном шаблоне модуля, если её пакет
  отдал `viewUrl` ([событие](03-events.md#куда-ведёт-ссылка-статьи)) и статью
  не правили руками; иначе `/note/document/<id>/`. Ссылку переключает импорт:
  после правки статьи в `note` она поведёт в `note` со следующего импорта
  (агент раз в сутки или кнопка «Обновить статьи»);
- `noteUrl` — всегда документ `note`, `/note/document/<id>/` (с 1.2.0);
- `snippet` — простой текст до 300 символов (теги подсветки сняты);
- `text` — лучшие под вопрос фрагменты статьи, до 1500 символов, раздел статьи
  строкой `## …` перед фрагментом (с 1.3.0, [индекс фрагментов](#индекс-фрагментов-130)).
  Это контекст для модели: отдавайте её `text`, а не `snippet`. Статья вне
  индекса или индекса ещё нет — `text` равен `snippet`;
- `$limit` приводится к 1..20;
- `title`, `snippet` и `text` — простой текст без экранирования: в HTML выводите через `htmlspecialcharsbx()` / `BX.util.htmlspecialchars()`.

## Где ищет

- **По умолчанию — только в своём разделе** «ИИ: База знаний». Поиск ядра
  (`Bitrix\Note\Public\Provider\SearchProvider`) раздел не принимает —
  `SearchQuery` несёт только текст. Поэтому у `note` просится вчетверо больше
  результатов, и выдача фильтруется по разделу документа. Документы, открытые
  пользователю лично (раздел ядро не раскрывает), в выдачу не попадают.
  Раздел ещё не создан — пустой список.
- **Настройка «Искать по всей Базе знаний»** (`KB_searchall`, по умолчанию
  выключена) — по всем документам, которые видит пользователь, в том числе
  по чужим разделам.

Почему так: чат ИИ-помощника отправляет найденное модели. По умолчанию туда
не должно уходить ничего, кроме справки модулей; включить шире — осознанное
решение администратора.

В обоих случаях права проверяет поиск ядра по текущему пользователю. Нет
пользователя (агент, консоль) — пустой список. `note` не установлен — исключение.

Ответ держится в кеше 60 секунд (`Bitrix\Main\Data\Cache`, ключ —
пользователь, запрос, лимит, раздел, метка индекса).

## Как разбирается вопрос

Поиск `note` находит документ, только если в нём есть **каждое** слово
запроса (от трёх букв, с подстановкой `слово*`). Поэтому вопрос сначала
чистится (`Search\QueryNormalizer`, перенос `Rag::tokens()` shef.toolsai — там класс снят, живая копия здесь):

1. нижний регистр, стоп-слова прочь («как», «что», «на»…);
2. слова — к основе: «квоту» -> «квот», «настроить» -> «настро»;
3. остаются слова от трёх букв, без повторов, не больше шести.

Потом (`Search\ResultMerger`):

1. ищутся документы со всеми словами сразу;
2. набралось меньше `$limit` и слов больше одного — ищутся отдельно три самых
   длинных слова (самые редкие и точные; больше — лишние запросы к базе);
3. сведение: найденные всеми словами — выше, дальше по числу слов, по сумме
   оценок `note`, по порядку.

## Индекс фрагментов (1.3.0)

Поиск `note` ищет документ целиком и отдаёт сниппет подсветки — модели этого
мало: ответ на вопрос часто в середине статьи, а «все слова сразу» на живом
вопросе находит мало. Поэтому у модуля свой лексический индекс (RAG без
внешних сервисов и без эмбеддингов):

1. **Сборка** — после каждого импорта (`Import\Runner::reindex()`,
   `Search\IndexBuilder`): все документы своего раздела — и импортированные, и
   правленные руками (текст — как сейчас в `note`), и добавленные людьми;
   архив и корзина — нет. Статья режется на фрагменты по заголовкам `#`…`####`
   (`Search\Chunker`), длинный раздел — по абзацам до 1200 символов. Фрагменты —
   в таблице `shef_toolsaikb_chunk`, метка сборки — `SYS_indexversion`;
   сколько фрагментов — в строке итога импорта. Сбой сборки импорт не
   отменяет: ошибка в отчёте, поиск остаётся на прежнем индексе.
2. **Кандидаты и права** — по-прежнему поиск `note` с правами сотрудника
   (как выше), но с запасом: до 20 документов (в своём разделе — ×4 до
   фильтра) и добор по трём самым длинным словам всегда. Индекс не решает,
   что сотрудник видит: документа, которого `note` ему не отдал, в выдаче нет.
3. **Порядок и текст** — BM25 по фрагментам кандидатов (`Search\Bm25Index`:
   k1 1.2, b 0.75, заголовок статьи и раздела весит втрое, слова —
   `QueryNormalizer::tokens()`). Оценка статьи — её лучший фрагмент; в `text`
   идут до трёх лучших фрагментов в порядке статьи, в пределах 1500 символов.
   Документы вне индекса (чужие разделы при `KB_searchall`) — после, в
   прежнем порядке, со сниппетом `note`.

Индекс лежит в кеше (ключ — метка сборки) и строится заново только после
импорта. Таблицы или фрагментов нет (модуль обновлён, импорт ещё не прошёл) —
поиск работает как до 1.3.0. Правка статьи руками попадает в индекс со
следующим импортом (агент раз в сутки или «Обновить статьи»).

Таблица фрагментов — производная: удаление модуля убирает её всегда (и с
`savedata`), переустановка пересоберёт первым импортом.

## Ajax

```js
BX.ajax.runAction('shef:toolsaikb.search.find', {data: {query: 'квота', limit: 5}})
	.then(r => r.data.articles);
```

Фильтры ядра по умолчанию: авторизация, `sessid`, GET/POST. Запрос длиннее
1000 символов (без пробелов по краям) — ошибка; `limit` приводится к 1..20.
